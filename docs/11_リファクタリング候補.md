# リファクタリング候補

2026-11-08、0.4.0（読み上げを足した版）の時点で、構成と責務を見直した結果。機能を足すたびに `app` の中で増築してきたため、層の分け方と単一責務から外れている箇所をまとめる。技術的負債の返済は別の作業として進める。ここに書くのは候補で、着手する順番と範囲は作業を始めるときに決める。

## 前提：今の層

`docs/02_アーキテクチャ.md` のモジュール構成は、次の4層になっている。

| 層 | 今の置き場 | 本来の責務 |
| --- | --- | --- |
| 画面 | `app` の各 `*Activity`・`@Composable`・オーバーレイの `View` | 表示と操作の受け付け |
| 機能の流れ | `app` の `*ViewModel`・`LiveTranslator`・`ScreenTranslateService` | 認識・翻訳・読み上げをつなぐ |
| 共有の資源 | `app` の `EngineHolder`・`ReadAloud`・`ModelDownloads`・`ModelCatalog` | モデルの選択・読み込み・設定の保存・ダウンロード |
| 推論の部品 | `core-llm`・`core-ocr`・`core-asr`・`core-tts` | 1つの推論をインターフェースの裏で実行する |

`core-*` はおおむね単一責務に収まっている。問題は、上の3層がどれも `app` に同居し、パッケージの境界も機能別（`camera`・`conversation`・`screen`）と層別（`models`）が混ざっている点に集中している。

## 優先度：高（次の機能追加の前に直したい）

### 1. `EngineHolder` が翻訳モデルの全部を抱えている

- **今**：`object EngineHolder`（`app/.../EngineHolder.kt`、194行）が、使うモデルの選択と保存（SharedPreferences）、読み込みと読み直し、GPUを使うかの判定、GPUの初回準備、CPUの設定（スレッド・性能ヒント・CPUだけで動かす）の保存、速さの計測（`bench`）、読み込みの待ち合わせ（`awaitEngine`）をすべて持つ。`ModelState` も同じファイルにある。
- **問題**：設定の保存・モデルの生存期間・計測が1つのシングルトンに混ざり、単体テストできない（`Context` とグローバル状態に依存）。画面（`PerformanceCard`・`ModelSwitch`・`SettingsActivity`）から直接呼ばれている。
- **案**：設定の読み書き（`TranslationSettings`：モデル・CPU設定）、生存期間の管理（`TranslationEngineProvider`：読み込み・読み直し・`StateFlow<ModelState>`）、計測（`EngineBenchmark`）に分ける。画面はProviderの状態だけを見る。

### 2. 音声認識のモデルの持ち方が機能ごとにばらばら

- **今**：会話翻訳は `ConversationViewModel` がSenseVoiceを読み込み、モデルの場所も `ConversationViewModel.modelDir()` が持つ。テキスト翻訳の音声入力（`TranslateViewModel`）は、そのメソッドを借りて別にもう1つ読み込む。マイクの `MicRecorder` と `isChinese` も `conversation` パッケージから借りている。
- **問題**：テキスト翻訳が会話翻訳のViewModelに依存している（機能どうしの横の依存）。同じ約230MBのモデルを、画面を開くたびにそれぞれ読み込み直している。
- **案**：`EngineHolder` と同じ形で、音声認識の生存期間を `AsrProvider`（仮）にまとめ、`MicRecorder` と一緒に共有の層へ移す。`isChinese`・`sameAs` は `Language` の側（`core-llm`）へ寄せる。

### 3. `ReadAloud` が設定・再生・画面への通知を兼ねている

- **今**：`object ReadAloud`（116行）が、読むものの選択、声・速さ・段数の保存、`Speaker` の生成と保持、再生の状態（`speaking`）、マイクを無音にする判定（`isAudible`）、失敗の `Toast` を持つ。`ConversationViewModel` はマイクの音を処理するたびに `ReadAloud.isAudible()` を直接呼ぶ。
- **問題**：設定と再生の生存期間が混ざっている。`Toast` を出すのは画面の仕事。会話翻訳の「読み上げ中はマイクを無音にする」約束が、グローバルな関数呼び出しで暗黙につながっている。Supertonic 3（fp32のvocoderを含めて約220MB）を一度読むとアプリを閉じるまで手放さず、翻訳モデルと合わせたメモリの上限を考えていない。
- **案**：設定（`SpeechSettings` の保存部分）、再生（`SpeechPlayer`：`speaking` と `isAudible` を `StateFlow` で出す）、失敗の通知（画面が `StateFlow` を見て出す）に分ける。会話翻訳には「読み上げ中か」の `Flow` を渡す。使わない時間が続いたら、またはメモリが足りなくなったら（`onTrimMemory`）読み上げのモデルを手放す。

### 4. `ModelDownloads` の「追加のダウンロード」が場当たり的

- **今**：初回にそろえるファイル（`ModelCatalog.files`：翻訳0.8B・音声認識・漫画用OCR）と、後から設定で取るもの（2B、読み上げ）を、`start(extra = …)` の引数1つで切り替えている。エラーをどの欄に出すかは `lastExtra` を比べて決めている。
- **問題**：ダウンロードの単位（どのファイルの組か）が型になっておらず、同時に1組しか取れない。組が増えるたびに `lastExtra` と同じ比べ方が画面に増える。
- **案**：`ModelBundle`（初回のセット・2B・読み上げ）を型にし、組ごとに `StateFlow<DownloadState>` を持つ。`ModelCatalog` は組の定義だけにする。

## 優先度：中

### 5. 画面翻訳とカメラ翻訳の共通部品が `screen` パッケージにある

- **今**：カメラ翻訳（`camera`）が `screen` の `BatchTranslator`・`BoxColors`・`ColorSampler`・`selectTargets`・`SCREEN_TARGET`・`spToPx` を使っている。
- **問題**：どちらも「文字を認識して、選んで、まとめて訳し、重ねる」部品を共有しているのに、画面翻訳の持ち物になっている。画面翻訳を直すとカメラ翻訳が壊れ得る。
- **案**：共通の部品を `overlay`（仮）パッケージへ移す。訳す先の言語の既定値（`SCREEN_TARGET`）は各機能の設定に分ける。

### 6. 設定の保存先が散らばっている

- **今**：SharedPreferencesを、`EngineHolder`（モデル・CPU）、`ReadAloud`（読み上げ）、`LanguagePreference`（画面翻訳の言語）、`CameraSourcePreference`・`CameraTargetPreference`（カメラの言語）がそれぞれ直接開いている。
- **問題**：保存のキーと既定値が各所に散り、移行（キーの改名、旧形式の読み替え）も各所で別々に書いている（`CameraSourcePreference.legacy`）。
- **案**：設定の読み書きを機能ごとの小さなリポジトリ（`*Settings`）に寄せ、`Context` を受けるのはその層だけにする。DataStoreへ移すかは、そのときに決める。

### 7. 大きな画面のファイル

- **今**：`ConversationActivity.kt`（532行）は、画面の組み立てに加えて、会話ログの共有と保存、マイクの開始、デバッグ用のWAVの流し込みを持つ。`CameraTranslateActivity.kt`（386行）も、CameraXの設定・画像の変換・言語の選択の画面を1つに持つ。
- **問題**：変更の理由が違うものが1つのファイルにあり、差分が読みにくい。
- **案**：`ConversationActivity` は、カード（`FaceCard`・`SharedCard`・`UtteranceCard`・`LiveCard`）、操作の欄（`Controls` と各メニュー）、ログの書き出しにファイルを分ける。カメラは、CameraXの準備（`startCamera`・`toUprightBitmap`）を画面の外へ出す。

### 8. `SenseVoiceAsr` が音声区間の検出・区切り・言語の切り替え・認識を1つに持つ

- **今**：`core-asr` の `SenseVoiceAsr`（441行）が、VADの結果からの区切り、話し手の交代（言語の切り替わり）の検出、途中の認識、確定の認識を1つのクラスで持つ。
- **問題**：区切りの規則を変えるたびに、認識の呼び出しと同じクラスを触る。区切りの規則は実機の音声でしか確かめておらず、単体テストが無い。
- **案**：区切りと言語の切り替えの判定を、音声と認識結果の列だけを受ける純粋なクラスに分け、単体テストを付ける（`SpeechBuffer` と同じ扱い）。

## 優先度：低

### 9. `Language` が翻訳のプロンプトのファイルにある

`Language`（53言語の列挙）は `core-llm` の `Pfml3PromptBuilder.kt` にあり、OCR・音声認識・読み上げも使う。読み上げ（`Speaker`）と音声認識は言語を文字列のコードで受け、`zh-hans` などの変換を各所で書いている。`Language` を独立したファイル（できれば共通の小さなモジュール）へ移し、各部品の境界で同じ型を使う。

### 10. デバッグ用の入口が本番のコードにある

`ScreenTranslateService` の `DEBUG_TRANSLATE`・`DEBUG_CONFIG` のブロードキャストと、`ConversationActivity` のWAVの流し込みは、実行時に `FLAG_DEBUGGABLE` を見て止めている。評価用の `BenchActivity` と同じく `src/debug` へ移せば、正式版のコードから消せる。

### 11. 読み上げの段数・スレッドの定数と計測の記録

`SupertonicSpeaker` の段数の範囲・既定値・スレッド数は、実機の計測（`docs/04_会話翻訳.md`「読み上げ」）に基づく定数になっている。端末を増やして確かめるなら、翻訳の「パフォーマンス」と同じく、設定と計測の画面に寄せる。

## 進め方の注意

- 振る舞いを変えないリファクタリングと、機能の変更を同じコミットに混ぜない。
- 1〜4は互いに似た形（設定・生存期間・状態の分離）なので、最初に1つ（`EngineHolder` か `ReadAloud`）で形を決め、残りを同じ形にそろえる。
- 画面翻訳の部品（5）を動かしたら、`tools/run-bench.ps1` で変更前後を比べる（`CLAUDE.md`）。会話翻訳（2・8）を動かしたら、`docs/04_会話翻訳.md`「動作確認の方法」のWAVで、カードの区切りと訳が変わらないことを確かめる。
- 構成を変えたら `docs/02_アーキテクチャ.md` と `CLAUDE.md` の構成の早見表を直す。
