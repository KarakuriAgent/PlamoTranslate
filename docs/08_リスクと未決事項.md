# リスクと未決事項

更新日：2026-11-06

実測で決める事項と、結果が悪かった場合の代替案をまとめる。決まった事項は、判断と根拠を「決まった事項」へ移す。

## 実測で決める事項

| 事項 | 決める時期 | 現時点の案 | 決め方 |
| --- | --- | --- | --- |
| 音声認識エンジン | 今のエンジンに不満が出たとき | SenseVoice Small＋Silero VAD（2026-11-06に実装。作者の評価は「音声入力の正確さは結構いい」）。2026-11-09から、SenseVoiceが聞けない相手の言語だけ補助のモデル（Canary・Parakeet・Qwen3-ASR）で聞く（実機未確認） | Nemotron 3.5 ASR Streamingなどと精度・遅延・言語判定を比べ、作者と決める（`docs/04_会話翻訳.md`「音声認識の候補」）。ドイツ語の補助にどれを使うかは実機で決める |
| 翻訳モデルの既定 | 作者が会話翻訳を2Bで話して試したとき | 既定は0.8B。作者は2Bを選んで使っている。2Bは約2.5倍遅いが、口語の難しい文54文で取り違えが7件→4件に減った（2026-11-06、`docs/03_翻訳コア.md`） | 会話翻訳で2Bの途中訳（0.5秒ごと）が追いつくかを作者が確かめて決める。2Bを既定にするなら、初回のダウンロードに2B（約1.8GB）を含めるかも決める |
| 履歴の扱い | 会話の訳に不満が出たとき | 会話翻訳には今は文脈も履歴も渡していない（背景の `context` を渡すのはカメラ翻訳の表・メニューのモードだけ）。案は方向別の履歴＋共通の文脈 | 異なる方向の履歴を混ぜる方式と訳文を比べる |

## 決まった事項

| 事項 | 決定 | 根拠 |
| --- | --- | --- |
| 翻訳の実行先 | GPU（OpenCL、全層） | REDMAGICがCPUクロックを1.79GHz程度に抑えるため。CLIでプロンプト処理がCPUの約5倍、訳文は一致（2026-11-05、`docs/00_現在地.md`） |
| 量子化形式 | Q4_K_M | GPUではQ4_0と速さが同程度（2026-11-05） |
| 画面翻訳のOCR | ML Kit（日・韓・中・英字）と漫画用OCR（PP-OCRv6 manga）を併用し、行ごとに選ぶ。モードの切り替えは作らない | 縦書きの中国語の文字の正解率と、英語の漫画の読み取り（`docs/05_画面翻訳.md`「判断の記録」） |
| 画面翻訳の言語 | 自動判定を既定にし、浮遊ボタンの長押しで指定もできる | 作者の要望（2026-11-05） |
| 会話翻訳での実行資源 | 翻訳はGPU、音声認識（SenseVoice・VAD）はCPU 4スレッド＋1スレッド | 同時に動かして、途中訳が途中の文字の0.1〜0.9秒後に付き、確定訳の時間も変わらなかった（2026-11-06、`docs/04_会話翻訳.md`「評価」） |
| ONNX Runtimeの重複 | sherpa-onnxは、ONNX Runtimeを内部に静的に組み込んだAARを使う。x86用だけ別ファイルの `libonnxruntime.so` があるので同梱から外す（アプリはarm64だけ） | 漫画用OCRのONNX Runtime 1.31.1とライブラリ名がぶつからない（2026-11-06） |
| 翻訳モデルの選択 | 0.8B（既定）と2Bを作者が選べる。初回のダウンロードは0.8Bだけで、2Bは選んだときに追加で取る | 作者の要望「2Bも選べるようにして、翻訳品質と速度の違いをチェックしたい」（2026-11-06）。2Bは約2.5倍遅いが意味の取り違えが減った |
| カメラ翻訳の映像の取り込み | CameraX 1.4.2（`camera-camera2`・`camera-lifecycle`・`camera-view`） | 作者の要望「カメラ画像のリアルタイム翻訳」で、大きな依存の追加を作者が了承した（2026-11-06）。APKに増えるネイティブライブラリは数十KB（`docs/02_アーキテクチャ.md`「APKの中身」） |
| カメラ翻訳の読み取り | 1行ずつ読み、コマをまたいで行を追って多数決で原文を決め、表示と翻訳は段落ごとにする | 大きなまとまりのままでは読み揺れで同じ文としてそろわず訳が出なかった。作者の提案「重なる枠は1段落として統合した方が欠落が無くなる」（2026-11-06、`docs/10_カメラ翻訳.md`） |
| 会話の確定までの待ち | 話し終わりは無音2秒で確定させる。話し手が代わったら（言語が変わったら）2秒を待たずに区切る | 作者の要望「ライブで翻訳が見えるから、発話の終わりは2秒くらい待ってほしい」「高速で話し合うとき、2秒待ってどうぞとするのは会話のキャッチボールとして良くない」（2026-11-06）。要件の「確定訳1.5秒以内」には届かないが、途中訳が先に出る |

## リスクと代替案

| リスク | 影響 | 代替案 |
| --- | --- | --- |
| Nemotron 3.5の多言語版がsherpa-onnxのストリーミング認識で動かない | エンジンを比べるときの候補が減る | 今のSenseVoiceの疑似ストリーミングで十分なら比べない。ONNX Runtimeで直接ストリーミング処理を書く方法もある |
| 長い発話で、途中の文字のための認識し直しが重くなる | 途中の文字の更新が遅れる | 認識し直す間隔は、1回の認識時間の3倍より短くしない。カードは14秒で区切る |
| 長時間の連続稼働で発熱し、速度が落ちる | 会話の後半で遅れる | 途中訳を止めて確定訳だけにする省電力設定を用意する。REDMAGICの冷却ファンを有効にした状態でも測る。30分の連続稼働はまだ測っていない |
| 話し手の交代を言語で見分けている | 同じ言語の2人の会話や、1人が言語を混ぜて話すと区切りがずれる | 今の使い方（日本語と相手の言語）では起きにくい。困ったら区切りの手動ボタンを足す |
| llama.cppのplamo3対応に不具合がある | 訳文が崩れる、または読み込めない | llama.cppの新しいコミットへ上げる。Hugging FaceのGGUFリポジトリの議論も確認する |
| モデルのライセンス | 配るときに条件が付く | PLaMoは、学習・趣味などの個人利用と非商用利用が事前登録なしで無料（モデルのページの記載、2026-11-06に確認）。アプリを無料で配る使い方はこの範囲と判断している。重みはアプリに同梱せず、使う人の端末が公式の配布元から取るので、アプリの配布は重みの再配布にならない。PP-OCRv6 mangaはApache-2.0、Silero VADはMIT。音声認識の補助のモデルは、Canary・ParakeetがCC-BY-4.0（作者の表示と、手を加えたこと＝ONNX・int8への変換の表示を「このアプリについて」に出す）、Qwen3-ASRがApache-2.0。SenseVoiceのモデルライセンス（FunASR）の本文は確かめていない。商用で使うなら、PLaMoの商用の条件とSenseVoiceの条件を確かめる |
| ほかの端末で動くか確かめていない | ほかの端末で落ちる、遅すぎる | 作りとしては、Qualcommの端末はGPU、それ以外はCPUで動く（`docs/02_アーキテクチャ.md`「GPUとCPUの切り替え」）。確かめたのはREDMAGIC 11 Pro（GPU）と15T Pro（CPU、2026-11-08）だけ。CPUの速さは、2026-11-05のCLIの測定でGPUの1/2〜1/3程度（8行まとめの翻訳 GPU 0.97秒、CPU 2.55秒）。古いAdreno（740・750）でOpenCLのカーネルが動かないときは、GPUでの読み込みに失敗してCPUでやり直す作りにした。読み込めても訳文が崩れる場合は、機種を見てCPUに切り替える |
| 端末のメモリが足りない | 翻訳モデル・音声認識の読み込みに失敗する | モデルは合わせて1GB弱（0.8Bのとき）をメモリに置く。6GB以上の端末を目安にする。2B（ファイルで1.8GB）を選ぶと、さらに1GB余り多く要る見込み（ほかの端末では測っていない） |

## 作者に確認すること

- 主に読む漫画の言語。これまで中国語・韓国語・英語の漫画で評価した。日本語の縦書き漫画を訳す必要は今のところ無い（訳先が日本語のため）。
- 会話翻訳で相手言語の初期値を韓国語にしてよいか。
